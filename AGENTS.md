# Repository operating contract

Read `README.md`, `docs/THESIS.md`, `docs/PROBLEM_MAP.md`, `docs/ENTRY_STRATEGY.md`, and `DECISIONS.md` before changing direction.

- Work problem-first. Every substantial task must name the problem ID it advances and the evidence that would change the decision.
- Separate company claims, reproducible evidence, deployment evidence, and project inference. Record an official or primary source and verification date for non-obvious claims.
- A polished demo is not acceptance. Experiments need a baseline, perturbations, failure artifacts, and quantitative readback.
- Do not reduce the project to dashboards or integration glue. Infrastructure work is valuable only when it measurably improves the embodied learning loop.
- Keep course repositories independent. Never publish coursework or nested repository history through this root repository.
- On Shawn's machine, `~/code/memory` is the optional private source for personal facts and prior decisions. Search it only when relevant; never copy secrets or sensitive personal details into this public repository. Public project decisions belong in `DECISIONS.md`; private facts remain canonical in memory.
- Run `python3 scripts/validate_research.py` before committing research-map changes.
- Current measured or configured facts live in one `CURRENT-STATE.json` per system (standard: the `current-state` skill; check: `python3 ~/code/claude-config/scripts/state_check.py <file>`). MicroDuck: `microduck-sim/CURRENT-STATE.json` (IMU rate and delay, servo read drops, servo rail, walking policy and gains, power); its probes are `microduck-sim/guide/firmware/mac/robot_state_check.py`, which also gives `sim_suite.sh` the real-condition flags, and the suite marks each case `real` or `stress` (harsher, report only, never an accept/reject basis). Capture walk_wired stdout to `/tmp/duck_wired_<suffix>.out` beside `--log /tmp/duck_wired_log_<suffix>.jsonl` so the IMU rate stays measurable. Read values only from these files, never from memory files, DECISIONS history, logs, transcripts or code comments; put the path in every brief; when a measurement changes a fact, update its entry in the same turn and move the old value to `superseded`.
- OMX-F arm: current calibration, limits, gripper settings, bus and sim teacher live in `omx-local/CURRENT-STATE.json` (probes `omx-local/current_state_probe.py`, read-only). Read them only there, never from CALIBRATION.md, calib_spec.json, the runbook, code comments or memory. `vs_grasp.py` and `servo_grasp.py` refuse to start when its check fails; calibration scripts are not gated because they produce the new values. After a recalibration or measurement, update the entries in the same turn.
- Before answering or changing MicroDuck hardware, training or scope, read `microduck-sim/PROJECT-CONTEXT.json` and its linked training evidence. Use the context-linked workflow, handbook and verifier as the current entry points. Run that verifier with `--scope design` for hardware-plan handoff and `--scope project` for complete-project acceptance; it routes to `microduck-sim/guide/verify_current_design.py` (release, gate receipt, guide build, screw stock, live pages; project scope adds the physical acceptance list in `current_build.design_gate`). A passing design check cannot close physical commissioning or the visual-pickup goal.
- Before any MicroDuck simulation study, list the sim mass manifest's parts against the hardware on the robot now (backpack, head boards, audio) and the latest `DECISIONS.md` entries; take supply and sensor values from `microduck-sim/CURRENT-STATE.json`, not from DECISIONS history. A missing or outdated part is fixed in the model, with sourced masses and positions, before any run; COM or IMU offsets never stand in for a known missing part. Then check the model against the robot's real static stances before using it for a decision.
- MicroDuck release work is time-boxed. During a print or guide release run only the release gate (`build_solids.py`, `pairs.py`, `steps_audit.py`, `cables.py`, slicing, page probes); do not start studies, sweeps or tables that are not in the gate. The bounded runner (`build-pack-20260913/redesign-20260913/head-redesign-20261008/run_bounded_cad.py`) clamps every job to 10 minutes unless `MICRODUCK_CAD_LONG_JOB_OK` carries Shawn's explicit go, logs every start and end to `.cad-queue.log`, and answers `--status` with the current lock holder; a session that dispatches CAD work checks `--status` before reporting progress. A gap an agent reports in its own hand-back is not a task: scope grows only on Shawn's word. Reuse existing conclusions: the jaw pose-cap study (`guide/firmware/pi/jaw_pose_caps.json`) is rerun only when jaw, neck or head geometry changes, never for clips, wires or screws. Report remaining work as concrete steps, not hour estimates.
- Before releasing any MicroDuck print file, rebuild the assembly guide from that geometry and run the print gate: `microduck-sim/guide/content/interference-audit/run_gate.py` runs `build_solids.py`, `pairs.py`, `steps_audit.py` and `cables.py` under the bounded runner (80 seconds on 2026-10-13) and writes `gate-receipt.json` bound to the guide data. Final-pose contacts that are designed (seams, press fits, mated plugs) are listed with their reason in `pair_classes.py`. Release only with zero path collisions, no new final-pose part overlap and no new mid-cable penetration. Those four scripts are the whole gate: `steps_audit.py` covers assembly paths and connector insertion (plug plus wire exit), `pairs.py` the final poses, `cables.py` mid-cable penetration. A check that none of them implements is a study, not a gate item. Explain each connection method in plain words and confirm it with Shawn before it shapes printed geometry.
- Before MicroDuck procurement work or delegation, read `microduck-sim/build-pack-20260913/procurement/sourcing-policy.json` and its README. Preserve sourcing holds independently of engineering requirements; available stock and historical carts cannot release them. Regenerate the BOM/cart plan and run `test_sourcing.py` plus `verify_pack.py` in that directory before a purchasing handoff. Acceptance requires zero held items in purchase rows or mapped current carts; unmapped cart lines block handoff.
